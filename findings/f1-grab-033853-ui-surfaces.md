## Save-path filtering: what code establishes and what it does not

Thus `wpa_pskcred0/1` on the advanced AP form matches the `wpa_psk` substring rule; `passWord` in content sharing and the DDNS password fields also match. This corrects any reading of the matcher as requiring exact field-name equality.

The basicview pages load `/js/main-min.js` from `home.lp.html:13`, and their save controls use the shared `#save-config` convention (`basicview-wifiguest-modal.lp.html:30`, `basicview-wifipsk-modal.lp.html:32`, and their 5 GHz counterparts at `:28,:30`). Those pages' names `wifi_pswd`, `wifi_pswd_new1`, `wifi_pswd_new2`, and `pswd` do not match the enumerated AES field-name rules. The captured `home.lp` does not load `asmcrypto-min.js`; its basicview inline scripts contain no AES transform or direct AJAX/POST transform. This is evidence about the visible client path and matcher only. **UNKNOWN:** whether all basicview saves actually reach this shared handler in the deployed browser state; whether another runtime layer transforms values; whether the server expects/plainly accepts those values; and what the request body would contain. Do not report plaintext-on-wire or a transport weakness without a controlled request observation.

Likewise, the visible `ipsec_psk` field does not match the AES matcher (`modals__l2tp-ipsec-server-modal.lp.html:18`); its route-specific JS was not captured. That is an incomplete client-side protection lead, not a claim about transmitted or stored form. ## Trust boundaries and security leads

The rendered shell is the browser trust boundary for modal fragments and same-origin JSON/status responses. The relevant sinks are in shared UI code. Each item below is a **HYPOTHESIS** about reachability/encoding until a controlled source-to-sink test demonstrates that an untrusted value reaches the sink as markup or as a parsed query parameter:

1. **Backend response to DOM HTML:** `artifacts/ui/main-min.js:306–308` applies response values to `.val()` when a matching named input exists and `.html()` otherwise. Status nodes in the Internet forms include ID-only display spans. Whether an attacker can control any response value, and whether the browser parses it as active markup, is not established.
2. **Device edit response:** `js__device-min.js:10–11` inserts the edit response with `.html()`. The response source is same-origin backend output in the observed client design; a controllable stored name/icon or unsafe server template would need to be demonstrated.
3. **Wireless card rows:** `js__004_wireless.js:19` concatenates response data into row HTML. The corresponding query response was not captured; the bare route's 0-byte 200 cannot establish the source data or vulnerability.
4. **AP query construction:** `js__wireless-ap-modal-newEM.js:319` concatenates SSID-related inputs into a GET query. The AP SSID field has a 32-character limit but no restrictive markup pattern (`modals__wireless-ap-modal-newEM.lp.html:37,48`); encoded delimiter handling and server parsing are unknown. This is a parameter-boundary test lead, not proof of injection or a reachable exploit.
5. **Internet DNS control replacement:** `js__internet-dns-min.js:3–4` builds replacement input markup from a value. The value's source, escaping, and whether it can be attacker controlled are not proven.
