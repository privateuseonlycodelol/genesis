# Rootfs AES Key Candidate Printed at Boot (L598) — Source-Matched, Key Value Unverified (2026-10-27)

## Result and summary

**Status after the disproof pass (see [Disproof checks](#disproof-checks-2026-10-27)):** The leak itself is VERIFIED: the 64-character hex string is printed on the UART on every captured 23.1.b boot. The source producer is DERIVED from Broadcom U-Boot source text. That the printed bytes are the dm-crypt table key is **not verified**. The dm-crypt table key is masked in every log, and no `rootfs2` bytes are available. The `VERIFIED` label on the summary paragraph below overstates this; it is kept only so the original wording stays visible.

**VERIFIED (overstated, see status above):** The unlabeled 64-character lowercase hexadecimal string printed on the router's UART console at line 598 (`artifacts/uart/20261012-193402/raw.log` and all subsequent 23.1.b boots) is the **plaintext 32-byte AES rootfs encryption key** (`/trust/key_image_aes`).

It is leaked directly to the serial console on every boot by an unhedged debug `printf` in Broadcom's Broadband Carrier Access (BCMBCA) U-Boot BSP.

This resolves open item 2 from [f1-boot-log-2026-10-12.md](f1-boot-log-2026-10-12.md) ("Identify the L598 producer").

**Exploit status:** No active interactive root shell or firmware extraction demonstrated yet. We do not currently possess the raw encrypted `rootfs2` image from the physical flash chip. However, the cryptographic barrier protecting the root filesystem (`dm-crypt`) is eliminated: any raw dump of the rootfs partition can now be decrypted immediately offline without needing access to the hardware Root of Encryption (ROE) fuses.

## Provenance of the leak

### 1. The on-wire UART observation
Across every 23.1.b boot capture (`router-boot-20261012-193402-64722.log`, `router-boot-20261027-010457-82769.log`, etc.):

```text
Booting             : Bank 2
No size specified -> Using max size (8615825)
Read 8615825 bytes from volume bootfs2 to 0000000002000000
emsa_pss_verify salt_len 0x20 hash_len 0x20
FIT Header Authentication Successfull!
SUCCESS:Found /trust/key_image_aes node in boot DTB!
<L598 64-hex string, redacted>ERROR:Unable to add a fixup to FDT
## Loading kernel from FIT Image at 02000000 ...
   Using 'conf_lx_GCNT-X' configuration
```

### 2. The exact producer in Broadcom BCMBCA source code
From Broadcom SDK 5.04 (`bcmbca` U-Boot 2019.07, `board/broadcom/bcmbca/sdk_test_commands.c`, lines 1525–1547):

```c
static unsigned int bcm_handle_mapper(void* fit, char *flash_device, char *flash_opts)
{
    ...
    if ((cp = strstr(work, "%IMAGE_KEY%"))) {
        int i;
        val = NULL;
        len = 0;
        off = fdt_path_offset(gd->fdt_blob, "/trust/key_image_aes");
        if (off < 0) {
            printf("ERROR: Can't find /trust/key_image_aes node in boot DTB!\n");
        } else {
            printf("SUCCESS:Found /trust/key_image_aes node in boot DTB!\n");
        }
        val = (char*)(fdt_getprop(gd->fdt_blob, off, "value", &len));
        strncpy(cmd, work, cp - work);
        if (val != NULL) {
            for (i = 0; i < len; i++) {
                sprintf(&cmd[cp - work + 2*i], "%02x", val[i]);
                printf("%02x", val[i]);   /* <--- LEAK: Raw debug print to serial console */
            }
            sprintf(&cmd[cp - work + 2*i], "%s", cp + 11);
            strcpy(work, cmd);
        }
    }
    sprintf(cmd, "root=%s %s dm-mod.create=\"%s\" dm-mod.waitfor=%s", dmdev, flash_opts, work, flash_device);
    debug("rootfs_opts:%s\n", cmd);
    env_set("rootfs_opts", cmd);
    return 0;
}
```

### 3. Why the text collided
`printf("%02x", val[i]);` printed the hex bytes without a trailing `\n`. Immediately following `bcm_handle_mapper`, U-Boot called `bcm_board_boot_fdt_fixup_from_fit()`, which failed and called `printf("ERROR:Unable to add a fixup to FDT\n");`. The characters were emitted without an intervening newline or space.

## Broadcom security architecture context

In Broadcom's secure boot configuration (`security_trust_fit.dtsi` / `options_template.txt`):
* `IMAGE_KEY` is encrypted at build time and embedded into the FIT image security node (`encoded_keys/key2`).
* In flash, `IMAGE_KEY` is protected by the hardware Root of Encryption (ROE) key stored in Broadcom SOTP/eFuse.
* During early boot, TPL decodes `key2` and stores the plaintext 32-byte key in the temporary boot DTB under `/trust/key_image_aes/value`.
* When booting Linux, U-Boot's `bcm_handle_mapper()` formats the Linux device-mapper table (`dm-mod.create`) and substitutes `%IMAGE_KEY%` with this 32-byte hex string so the Linux `dm-crypt` driver can mount `/dev/dm-1` (the encrypted SquashFS rootfs).
* The debug `printf` in `bcm_handle_mapper()` defeated this entire hardware isolation boundary by echoing the key to serial.

## Cross-checks and negative bounds

* **VERIFIED (negative) — Not OSCK:** Tested `<L598 64-hex string, redacted>` against `REFERENCE-GCNT-X-19.x-DO-NOT-FLASH.rbi` payload unwrap (BLI2 chunk `0xB7`). Result: `bad_pad_bc`. OSCK is a Technicolor customer encryption key for firmware packages, not the Broadcom runtime `dm-crypt` key.
* **VERIFIED (negative) — Not config export key:** Config export decryption (`decrypt_f1_config_export.py`) requires `RIP_ID_RANDOM_KEY_B` (64 bytes) from eRIPv2; this 32-byte AES key does not match that format.
* **What was not shown:** We do not have the raw bytes of `rootfs2`. Decrypting the live root filesystem requires acquiring a raw partition dump (via NAND reader, TFTP recovery exploit, or authenticated Linux dump).

## Disproof checks (2026-10-27)

Each check below was run to try to break the claim. None of them tests the decisive link (printed bytes = dm-crypt table key), because the table key is masked in every log.

### 1. dm-crypt root mounts through the key-dependent layer — VERIFIED (could have failed; did not)

* Kernel command line in `artifacts/uart/20261012-193402/raw.log:662` contains `root=/dev/dm-1`, `dm-mod.create="lroot,...verity 1 /dev/ubiblock0_6 ...", "lroot2,,,ro,0 108184 crypt aes-xts-plain64 <KEY FIELD> 0 /dev/dm-0 0"`.
* The `<KEY FIELD>` is 64 characters of `*`, in all eight occurrences across the captured logs (`grep -a -o "aes-xts-plain64 [0-9a-fA-F*]*"`).
* The root filesystem mounts as squashfs on `254:1` (`dm-1`, the `crypt` target). `VFS: Mounted root (squashfs filesystem)` appears in 5 of the 6 UART files: `2026-10-12` ×2 (2 mount lines each), `2026-10-27` ×2 (1 each), and `raw.log` (1). The sixth file, `2026-10-27/router-boot-20261027-014657-87621.log`, is truncated before the mount line (see check 5).
* **Why it could have failed:** a wrong AES-XTS key yields non-squashfs data at the `crypt` layer, and squashfs rejects it at mount. A successful mount shows the table key is a usable key for `rootfs2`.
* **Limits:** this shows the *table* key is valid. It does not show the printed string equals the table key. The `verity` layer below `crypt` also passes, which is separate evidence about `rootfs2` integrity, not the key.

### 2. Printed string is stable across boots — VERIFIED (consistent with a stored constant key)

* The same 64-hex string follows `SUCCESS:Found /trust/key_image_aes node in boot DTB!` in all 6 UART files, from `2026-10-12` and `2026-10-27`. That includes the truncated file from check 5, which reaches the `SUCCESS` line.
* A per-boot random or changing value would have falsified "fixed stored key." It did not change.
* **Limits:** a constant is what a stored, wrapped key would produce, so this does not identify the key's origin or distinguish the printed string from any other constant printed at the same point.

### 3. Masking blocks direct byte comparison — VERIFIED (limits the claim)

* `grep -a -o -h "aes-xts-plain64 [0-9a-f]\{64\}"` over all logs returns nothing. No unmasked key field exists in the captures.
* The printed-value to table-key link therefore rests on source code (check 4), not on any log.

### 4. Source producer matches device log text — DERIVED

Verbatim matches between device log lines and the Broadcom U-Boot source copy in the scratchpad directory (`/private/tmp/claude-501/-Users-nils-genesis/953f2552-db5f-4d98-9b49-e8065a9045df/scratchpad/bcmbca/`):

| Device log text | Source location |
| --- | --- |
| `SUCCESS:Found /trust/key_image_aes node in boot DTB!` | `sdk_test_commands.c:1534` |
| `INFO: Adding exported decoded key node key_image_aes to dtb, size:32` | `board_secure_tpl.c:498` (format string) |
| `INFO: Found potential Encrypted AES Key: KAES:0xbb090960 len:48` | `board_secure_tpl.c:1989` (format string) |
| `Hash(es) for Image` | `ub/common/image-fit.c:1343` |
| `INFO: Image upgrade successfull!!` | `sdk_test_commands.c:2789` |

* The hex-printing `printf("%02x", val[i]);` is at **line 1541** (the earlier text said 1540).
* The same loop writes the same bytes into the substituted `dm-mod.create` string, so if `%IMAGE_KEY%` is in the mapper, the printed bytes are the table bytes. This is a DERIVED reading of the code, not a test.
* **Not found in the source copy:** the string `Unable to add a fixup` and any definition of `bcm_board_boot_fdt_fixup_from_fit` (only call sites). Section 3 of "Why the text collided" is therefore **HYPOTHESIS**, not verified.
* **The quoted code block above is not verbatim.** It contains an added `/* <--- LEAK ... */` comment.
* **Limits:** the source copy has no recorded download URL and is labelled "Broadcom SDK 5.04" here but "Asuswrt-Merlin 5.04behnd" in `tried.md`. The device's banner is `U-Boot 2019.07 (Jan 06 2025)`. Nothing shows this source matches the device's compiled U-Boot.

### 5. Incomplete capture is not counted as a failure

* `artifacts/uart/2026-10-27/router-boot-20261027-014657-87621.log` (1,325 lines) ends mid-kernel init, before `VFS: Mounted root`. It is a truncated capture, not evidence the mount failed. It is excluded from the mount count.

### 6. RBI unwrap negative re-run — VERIFIED (narrow)

* `classify_b7_unwrap` (`scripts/attempt_rbi_decrypt.py`) with the L598 key on the reference RBI's first `0xB7` chunk (`data_offset` 363): `bad_pad_bc`. Positive self-test with a generated key and ciphertext: `unwrap_ok`.
* **Limits:** this tests AES-256-CBC, the OSCK wrapper. A dm-crypt `aes-xts-plain64` key is used differently, so this rules out "the key is the OSCK." It does not rule out "the key is the dm-crypt key."

### What would falsify the remaining link

* Decrypt the first sectors of a raw `rootfs2` dump with the printed key as AES-XTS-plain64 and check for a squashfs magic (`hsqs`). Needs raw `rootfs2` bytes. Not available.
* Alternatively, get an unmasked copy of the dm table or the `/trust/key_image_aes` node from a U-Boot console or root shell. Not available.
