## Password fields on save

**VERIFIED** in `main-min.js` and `asmcrypto-min.js`.

On `#save-config`, a field is encrypted when its name matches any of: `wpa_psk`, `passWord`, `passwordcred`, `wep_key`, `ddns_password`, `ddnsv6_password`, `cwmpAcsPass`, `connectionrequestPass`, `wpa3`, `password@cred`, `password.` followed by digits (literal dot; corrected in the [later exact-filter review](f1-grab-033853-auth-crypto.md)). Table row edits encrypt only an input whose name is exactly `password`.

The call is `asmCrypto.AES_CBC.encrypt(plaintext, session_key, "a", iv)`. In this asmcrypto build that function is `U(data, key, padding, iv)`. The string `"a"` is the padding argument. `!!"a"` is true, and true selects PKCS#7 (pad byte equals the pad length). It is not the IV.

The IV is 16 bytes from `crypto.getRandomValues`, turned into a binary string with `String.fromCharCode`. The posted value is hex(IV) concatenated with hex(ciphertext). The key is `sessionStorage.session_key`. This file only reads that key. `login.js` stores it as `hex_to_ascii(srp.key())`.

`srp.key()` returns the hex SHA-256 of the shared secret `S`. After `hex_to_ascii` that is 32 bytes, which is the AES-256 size this library accepts (`16`, `24`, or `32` only). A missing key is `null`. The library throws `unexpected key type` for a non-string, non-bytes key. It does not encrypt with an empty key.

`asmcrypto-min.js` is asmCrypto v0.0.12. Application code calls `AES_CBC.encrypt` from `main-min.js` only. SRP does not call it. `chart-min.js` and `media-min.js` contain no `.lp`, `.lua`, or `$.post`. `jquery-eval-patch.js` replaces `jQuery.globalEval` with a script-element insert. No caller of `globalEval` showed up in the other grabbed scripts.

## SRP in this `srp-min.js`

**VERIFIED** against the file and `scripts/f1_srp_login.py`. The grabbed script and that Python client use the same group and proof shape.

- `N` is the RFC 5054 2048-bit prime. `g` is 2. Pad width `q` is 256 bytes.
- Multiplier `k` is the fixed value `05b9e8ef…04e300` (the RFC 5054 SHA-1 `k`, with a leading zero so the hex length is even).
- `x`, `u`, the session key, and both proofs use SHA-256 via `jsSHA`.
- `u` is SHA-256 of `A` and `B` each padded to 256 bytes.
- `x` is SHA-256 of `salt || SHA-256(utf8(username + ":" + password))`, with the salt hex concatenated to the inner hex digest and then parsed as hex.
- Session key `K` is SHA-256 of the shared secret `S`, returned as hex. `key()` returns that hex only after the server proof matches.
- Client proof is SHA-256 of `4a76a9a2…29cc4c || SHA-256(utf8(username)) || salt || A || B || K` (hex concatenated, then parsed as hex). The fixed prefix equals SHA-256 of the 256-byte `N` XOR SHA-256 of the single byte `0x02`. It is the `H(N) xor H(g)` slot in the proof, with `g` not padded out to 256 bytes.
- Server proof expected by the client is SHA-256 of `A || M || K`, compared with `toUpperCase()`. The script has no string `M didn't match`. On failure it shows the server JSON `error` field, or the word `failed` when that field is absent. HTTP failures are passed through as the status number (`login.js` treats `403` as a CSRF refresh).
- Identify POST fields are `CSRFtoken`, `I`, `A`. Proof POST fields are `CSRFtoken`, `M`. Both go to whatever path `identify` was given (`/authenticate` from `login.js`, `/password` from `password.js`). The salt hex from the server is concatenated as received. `scripts/f1_srp_login.py` runs that salt through `even_hex` first. **Correction from the [later source/byte probe](f1-grab-033853-auth-crypto.md):** odd-length HEX is rejected by the browser’s jsSHA parser before a proof is produced; the Python client instead normalizes and continues. This is a client-input handling difference, not evidence that the live server sends odd salts. Shared-secret hex is padded to an even length on both sides.

Password change posts `salt`, `verifier`, and `cryptedpassword`. The verifier salt is generated by `h(8)` (32 random bits), and the verifier is `g^x mod N`. `cryptedpassword` is `sha512crypt(password, salt)` with a separate `h(16)` salt (64 random bits), not AES. **Correction from the [later source review](f1-grab-033853-auth-crypto.md):** `h(n)` adds one zero only for odd HEX length; it does not pad to a fixed width. These salts are even-length and at most 8/16 hex characters, rather than guaranteed exactly those lengths.

The earlier live body `M didn't match` is the server’s `error` string, not a comparison inside this script. For an ASCII username and password, and an even-length salt hex, the Python formulas match. Odd-length salt HEX is a failure-mode difference (browser rejection versus Python normalization), not a verified alternate proof. `login.js` still applies a legacy SHA-1 wrapper only when the page’s `userNames` / `legacySalts` lists contain the typed user. On the grabbed `login.lp` those lists are empty.
