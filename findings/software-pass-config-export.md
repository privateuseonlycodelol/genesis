# F1 configuration export — offline structural review

**Scope:** inspect the saved exports only as bytes and outer framing. No router/ISP traffic, credentials, configuration values, identifiers, response contents, or cookies are reproduced. For cross-version context, I reviewed the public repository README and issue cited below; I did not download or execute repository code, copy or try keys, derive keys, or decrypt content.

## Evidence

- **VERIFIED — artifact identity.** `artifacts/ui/readonly-control-20261012T021317Z/response-10.private` is 181,057 bytes and its SHA-256 is `430de53785019e67b4391a8adf296f7d0424a37e0863aab8c6bf4fb38193bdd0`, matching the parent-reported value. The saved summary record identifies it as the HTTP 200 response to `POST /modals/system-config-modal.lp` with action `export_config`; only method, path, status, size, and hash were inspected from that record.

- **VERIFIED — saved request summary records:** record 6 is a 200 GET to the system configuration modal with action `getbanksize`, 44 response bytes, and top-level JSON keys `success` and `banksize`. Record 7 is a 403 export POST (146-byte response); record 10 is the successful 200 export POST (181,057-byte response). **REPORTED (live-pass notes):** the bank-size value was `134217728`; the first export POST used the login-page CSRF token, while the successful retry used the authenticated gateway token. No token values are included here.

- **VERIFIED — two saved export envelopes.** `response-10.private` is 181,057 bytes (SHA-256 `430de53785019e67b4391a8adf296f7d0424a37e0863aab8c6bf4fb38193bdd0`); `response-13.private` is 181,089 bytes (SHA-256 `90d9833b519ddad18b183321196b8f0584ece549154ccb17081417a6434fe390`). Both have the same ordered, allowlisted header field names: `PREAMBLE`, `BACKUPVERSION`, `BOARDMNEMONIC`, `PRODUCTNAME`, `SERIALNUMBER`, `MAC`, `BUILDVERSION`, `CIPHERKEY`, `SIGNATUREKEY`. No header field values were printed.

- **REPORTED — cross-version format analogue.** The public [`technicolor-config-decrypt` README](https://github.com/antnks/technicolor-config-decrypt/blob/master/README.md) gives the same nine header names in a GANT-1, 17.1 example, and describes a newline-delimited header followed by a 16-byte per-export IV, data, and a 20-byte HMAC-SHA1 trailer. The public [hack-technicolor issue #72](https://github.com/hack-technicolor/hack-technicolor/issues/72) shows the same names in an owner-posted VANT-Z / 17.1 header, but provides no config binary. The README is internally inconsistent about AES size: its format prose says AES-128-CBC, while its command examples use AES-256-CBC. I do not rely on its cipher/key-length claim. These are reports about other devices and firmware, not proof about the GCNT-X / EWA1330 on 23.1.b.

- **VERIFIED — the `file(1)` RPF label is a weak match.** macOS `file` 5.41 reports `RAGE Package Format (RPF)` for both files. The installed rule source `/usr/share/file/magic/games:499-505` first matches only an offset-zero 16-bit little-endian value (`0x5250`); neither output includes a version-specific child match at offset 2 or an RPF version/entry count. This is evidence of the generic magic rule firing, not identification as an RPF archive. The local checkout has no RPF format specification or independent RPF fixture.

- **VERIFIED — framing consistent with `cfg_dec.py` assumptions.** In both exports, the `LF LF` delimiter begins at offset 235 and the first body byte is at offset 237, after 9 nonempty ASCII/UTF-8 header lines. They are LF-terminated (no CRLF or NUL); each contains `=`, one also contains `:`, and the observed names are listed above. This distinction matters: `cfg_dec.py`'s `readline()` loop stops after consuming the blank line, so its `stcry` body offset is 237 (`tools/secr/cfg_dec.py:34-40`). No header values were emitted. The body spans are 180,820 and 180,852 bytes. Under the unverified assumption that the first 16 body bytes are an IV and the final 20 bytes a digest, candidate cipher spans are 180,784 and 180,816 bytes respectively; each is block-aligned (11,299 and 11,301 16-byte blocks). Both exports have the same two-byte offset-zero prefix, and the first 16 body bytes differ. These observations establish repeated framing and a changing candidate IV, not the IV's actual role or cipher use.

- **DERIVED — the cross-version analogue raises, but does not prove, `cfg_dec.py`'s layout hypothesis.** The local exports' exact ordered header names, changing 16-byte candidate prefix, 20-byte suffix assumption, and block-aligned intervening spans agree with the *reported* analogue above. That makes a shared format family plausible. It does not establish that the candidate prefix is an IV, the suffix is an HMAC, or the body uses the reported cipher on 23.1.b; no HMAC was authenticated and no body was decrypted.

- **VERIFIED — no conventionally named length field was found.** `scripts/inspect_config_export_header.py` parsed only the line-header names and compared numeric values only for exact conventional length/size/count/offset field labels; it emits no values and allowlists output names. In both files there are zero such field names and zero numeric declared-length candidates, so no named length is available to compare with file, header, body, trailer, or candidate-cipher spans. The output's all-false span booleans are vacuous because there are no candidate lengths, not evidence of a malformed length. This does not rule out a length encoded inside an uninspected field value or body.

- **DERIVED — the `RPF` classification remains unproven.** `file -b` gives the same generic `RAGE Package Format (RPF)` label for both exports, and their first two bytes match. The local rule at `/usr/share/file/magic/games:499-505` fires on a two-byte offset-zero pattern; neither output includes a version-specific child match. Repeatedly matching that parent rule is not an independent RPF signature. The line-delimited header and aligned candidate spans do not identify a custom encrypted format either: no trailer was authenticated and no body was decrypted.

- **REPORTED — export implementation in related source.** The pinned Ansuel source snapshot in `artifacts/source-review/manifest.json` handles `export_config` as a POST, starts a transient export request, waits, and returns an octet-stream attachment named `config.bin` (`artifacts/source-review/gateway-modal.lp:68-105,309-314`). It does not document the inner byte format and is not confirmed to match this GCNT-X firmware.

## `cfg_dec.py` fit and limits

The script scans through a bare LF separator, treats the first 16 body bytes as the CBC IV, treats the final 20 bytes as HMAC-SHA1, uses `randb[0:32]` as the AES key and `randb[0:64]` as the HMAC key, then decrypts the intervening bytes (`tools/secr/cfg_dec.py:34-40,53-75`). Both samples satisfy its line-boundary and block-length preconditions. The field names `CIPHERKEY` and `SIGNATUREKEY` are observed header labels only; their meanings and relation, if any, to `cfg_dec.py` are unknown.

That is structural compatibility only. No key was supplied, no HMAC was checked, and no plaintext structure was verified. Also, the script only prints a warning when HMAC comparison fails and still writes the plaintext file (`:82-89`); it dumps supplied key material to stdout (`:53-61`). I did not run it on the private export.
