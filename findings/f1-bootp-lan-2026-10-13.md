# BOOT-P on the LAN — Windows pktmon (2026-10-13)

## Result

**VERIFIED:** during a listen-only capture on a Windows PC cabled to the owned F1, the gateway sent classic **BOOTP/DHCP requests** and **nothing answered**.

Ctrl+C on `pktmon` printed “flushing logs”. That writes the log. It did not delete it. The owner transferred `f1-bootp-2026-10-13.txt` and `f1-bootp-2026-10-13.etl`. Private copies: `artifacts/bootp/2026-10-13/` (gitignored). Text is UTF-16, 107,198 bytes. ETL is 419,430,400 bytes. No router HTTP request was made while reading them.

## What was on the wire

pktmon logged **154** port-67/68 events, all **Rx**. Every one is `0.0.0.0:68 → 255.255.255.255:67`. There is **no** Offer, Ack, or packet sourced from port 67.

The bootloader-sized flow (Ethernet **428** bytes, IP length **414**, UDP payload length **386**) is **68** logged copies of **17** unique requests from one client MAC, **00:27:45–00:28:12** local on 2026-10-13. Each request is:

| Field | Value |
| --- | --- |
| Opcode | **1** (BOOTREQUEST) |
| Hardware | Ethernet, length 6; `chaddr` equals the Ethernet source |
| `secs` | 0, then 1, 3, 5 … 27 (about every 2 seconds) |
| Flags | `0x8000` (broadcast reply requested) |
| ciaddr / yiaddr / siaddr / giaddr | all zero |
| `sname` in the logged prefix | empty |

**DERIVED:** 428 bytes is the same length U-Boot logged as `bcmbca_eth_send … len 428` when the port was down ([UART interaction](f1-uart-interaction-2026-10-12.md)). With a link, those frames leave the router. The earlier “BOOTP Reply timeout” is a missing server, not a dead Ethernet port.

pktmon kept **128** bytes of each frame, so the boot filename was missing there.

**VERIFIED (Wireshark full capture, 2026-10-13):** owner file `wan.pcapng-2` (898 KiB, archived `artifacts/bootp/2026-10-13/wan.pcapng`). **17** full **428-byte** BOOTREQUESTs from `00:1e:e3:76:83:61`, `secs` 0–27, broadcast flag. **Boot file name field (ASCII): `GCNT-X`** on every request — board mnemonic for Technicolor signed recovery images, not a `.rbi` path. No BOOTREPLY (`op` 2) to the router in this file. DHCP option area includes vendor-specific **option 43** (Technicolor `ST…` blob; product token `2242AD8AN` visible in hex). Still **no** TFTP transfer and **no** flash in this capture.

Two other source MACs also sent discovers (342-byte and 590-byte frames) in the same window. Those sizes are not the 428-byte bootloader frame. **DERIVED:** other LAN clients asking for a lease while the gateway was rebooting, not a second BOOT-P client. Addresses stay in the private ETL.

Windows also logged shorter “Drop” copies (414, 328, 576 bytes). **DERIVED:** the same three flows after the 14-byte Ethernet header, dropped by the Windows IP stack. They are not extra clients.

## What this does not do

No TFTP read, no firmware offer, no flash, no config key, no root shell. A recovery server was not running. Answering these requests with an image is a separate decision and was not done.

## Addendum (2026-10-27) — byte-exact re-read of `wan.pcapng`, offline only

**Scope:** re-parsed `artifacts/bootp/2026-10-13/wan.pcapng` with `tshark -V`/`-x` plus `scripts/decode_f1_bootp_leak.py` (new, tested: `python3 -m unittest test_decode_f1_bootp_leak` — 8/8 pass). No live router requests. All 17 GCNT-X BOOTREQUESTs in this capture are **byte-identical** to each other in every field below (checked across frames 277, 282, 296, 307, 326, 334, 344, 352, 356, 361, 367, 369, 373, 377, 387, 394, 396) — this is one boot session; a second, independently-booted capture has not been compared.

**VERIFIED — the 128-byte `file` field holds two null-terminated strings, not one:** byte offsets computed from the fixed BOOTP header layout (op/htype/hlen/hops/xid/secs/flags/ciaddr/yiaddr/siaddr/giaddr/chaddr/sname = 236 bytes, `file` field = next 128 bytes) place `file` at absolute offset `0x96`–`0x115` in frame 277. Exact bytes: `47 43 4e 54 2d 58 00 32 33 4b 4e 2f 30 2f 54 4c 00` + zero padding = `"GCNT-X\x00" + "23KN/0/TL\x00"` + padding. Wireshark's own dissector flags this with `[Expert Info (Warning/Undecoded): Trailing stray characters]` on the `Boot file name` field — it only expects one string. `"23KN/0/TL"` is not previously documented anywhere in this repo. **DERIVED (moderate confidence):** this reads as a clean, fully-formed second token (not a fragment), so it is more likely an intentional but undocumented second field — a build/variant/branch tag — riding along in the same buffer as the board mnemonic, than memory corruption. `23` as a leading token is consistent with the `23.1.b` firmware line already associated with this unit elsewhere in the repo, but that is **not** established here; **HYPOTHESIS**, not proof of version.

**VERIFIED — DHCP options 1 (Subnet Mask) and 3 (Router) carry non-address, ASCII-shaped garbage:** option 1 value bytes `55 2d 42 6f` decode as ASCII `"U-Bo"`; option 3 value bytes `2e 61 72 6d` decode as ASCII `".arm"`. Concatenated in on-wire order (option 1 then option 3 then option 6, all 4 bytes each) the 12 bytes read as `"U-Bo.arm\x00\x00\x00\x00"`. Wireshark's own dissector reports these as `Subnet Mask: 85.45.66.111` / `Router: 46.97.114.109` — syntactically valid-looking but semantically nonsensical for a BOOTREQUEST, which has no protocol reason to populate either field with a meaningful value at all (those are reply-side fields). **HYPOTHESIS:** this is an uninitialized or reused stack/heap buffer in the bootloader's BOOTP request builder leaking adjacent memory — possibly a fragment of a path or string like `.../u-boot.arm` — into option slots the code never explicitly sets. Not established: whether this is deterministic per-build (same every boot) or varies run to run; this capture only covers one boot session, so it cannot distinguish "static compiled-in filler" from "genuine stack garbage that happens to be stable within one run."

**VERIFIED (negative) — the option-43 (Vendor-Specific) blob does not walk as clean TLV:** `walk_vendor_specific()` on the real 55-byte blob (skipping the literal `"ST"` 2-byte prefix) stops almost immediately — a claimed length overruns the remaining buffer rather than reaching a sensible `0xFF` End within a consistent option set (regression-tested in `test_decode_f1_bootp_leak.py::test_captured_f1_vendor_blob_does_not_walk_cleanly_as_tlv`). This does not identify what `2242AD8AN` (already noted above) actually is; it only shows the surrounding bytes are not a well-formed generic vendor-option schema either, which is consistent with — but does not prove — the same leaked-buffer explanation as options 1/3.

**What was not shown:** no identification of `2242AD8AN`; no confirmation the file-field second string is a real version/variant code vs. coincidence; no comparison across independent boot cycles to test determinism; no TFTP interaction, no reply sent, no firmware offered.

**Why this matters for the next step:** if the bootloader's own request-encoding path is this casual about buffer initialization, that raises (not proves) the odds that its *reply*-parsing path — the one `f1-bootp-reply.ps1` would actually exercise — has similar weaknesses. This is a reason to prioritize, not substitute for, running the still-unexecuted BOOTP-reply test in [research composite](f1-research-composite-2026-10-13.md) item 1.

**Reproduction:**
```sh
tshark -r artifacts/bootp/2026-10-13/wan.pcapng -Y "frame.number==277" -x
python3 -m unittest test_decode_f1_bootp_leak   # from scripts/
```

## Addendum (2026-10-27) — active BOOTP reply test executed, first time

**Scope:** live, on-device. Windows PC cabled to the F1's LAN (Ethernet adapter statically addressed `192.168.1.1/24`), Mac UART watching (`/dev/cu.usbserial-0001`, 115200 baud). Router rebooted, `b` pressed at the U-Boot BOOT-P prompt. Windows ran a PowerShell BOOTP-reply listener (functionally `scripts/f1-bootp-reply.ps1`; the session actually used an owner-pasted variant, `C:\auto_bootp_test.ps1`, logic-identical — binds UDP/67, matches on `chaddr`, replies with `yiaddr`/`siaddr`/`file` set, no TFTP server running). This is the first time this project answered the router's BOOTREQUEST rather than only listening to it.

**VERIFIED — the reply script's wire format is RFC 951-correct:** independently checked the script's hardcoded byte offsets (`chaddr`@28, `yiaddr`@16, `siaddr`@20, `xid`@4, `file`@108) against the canonical BOOTP fixed-header layout computed from field sizes — exact match at every offset, including `file`@108, which is the same absolute value independently derived from the real captured packet in the base finding above (frame offset `0x96` minus 42 bytes of Ethernet/IP/UDP header = 108). Two independent derivations of the same number is a real cross-check, not a restated assumption.

**VERIFIED — owner-supplied Windows PowerShell transcript** (`Start-Transcript`, PID 10796, PSVersion 5.1.26100.7462, start `2026-10-27 01:04:30` end `01:06:34`): adapter reconfigured to `192.168.1.1/24`; listener bound UDP/67; two replies sent — `REPLIED to router! xid=e376b967 count=1` and `xid=e376ba62 count=2`; listener completed normally at its 120 s timeout; DHCP restored after. This is primary evidence from the replying side, not an inference from UART text alone.

**VERIFIED — UART, byte-exact from the owner-supplied capture file** (`~/Desktop/router-boot-20261027-010457-82769.log`, 115,702 bytes, SHA-256 `f3e83534e404b8e656593e55750c53a75b50b11e59a1ee229f59c2d80817b48e`; supersedes the earlier screenshot-based read in this addendum, corrects it): after the reply, the bootloader printed `TFTP from server 192.168.1.1; our IP address is 192.168.1.2`, `Filename 'GCNT-X'`, `Load address: 0x1000000`, then exactly:

```
Loading: *<BS>T T T T T T T T T
Retry count exceeded; starting again
BOOTP Reply timeout
Resetting the gateway

resetting ...
```

(`<BS>` = literal backspace byte, erasing a `*` busy-spinner char.) **Correction to the earlier version of this addendum:** this is not a silent fall-through to normal boot within the same cycle. **Ten** TFTP timeout retries (`T` characters, not one), then the device re-attempts the whole BOOTP negotiation (`starting again`), that second attempt also times out (`BOOTP Reply timeout` — this message follows a reply having already been successfully used once, so it describes the *second* negotiation round timing out, not "no reply was ever received"), and the device explicitly resets (`Resetting the gateway` / `resetting ...`, followed immediately by fresh `BTRM` boot markers in the log — confirmed full reboot, not a continuation). Normal Linux boot (`ehci-platform`, `usbcore: registered... usb-storage`, `bcm_thermal_drv` trip thresholds, `Linux version 4.19.235`) happens on the **next** power cycle, where the `*** Press b to enter BOOT-P ***` prompt reappears but `b` is not pressed again (no `Entering BOOT-P mode` line that time). No `#` TFTP-data-block characters appear anywhere — zero file bytes were ever received, consistent with no TFTP server running. No sign of a flash-write path, hang, or crash at any point — the failure path is bounded and deliberate (fixed retry count, then an explicit reset), just a harder stop than "falls through" implies.

The owner-supplied Windows transcript shows **two** replies sent (`xid=e376b967`, `xid=e376ba62`); the UART log shows only **one** successful `TFTP from server...` block before the reset. **DERIVED:** reply #1 was used for the TFTP attempt; reply #2 most likely arrived after — or during — the second, shorter internal BOOTP re-negotiation window and wasn't in time to prevent the reset. Not independently confirmed (would need the reply timestamps correlated against the UART's own timing, which isn't logged with wall-clock precision here).

**DERIVED — this demonstrates the bootloader accepts an unauthenticated network BOOTP reply and attempts TFTP recovery, which is the documented/intended function of BOOT-P mode, not a bypassed control.** BOOTP/DHCP has no authentication by protocol design; this result shows the mechanism functions on this unit, not that any check was defeated. The practically new thing established is a working, reproducible lab setup (script, addressing, timing) for the next question, not a vulnerability by itself.

**VERIFIED (new) — predictable transaction ID, not random:** the BOOTREQUEST `xid`'s upper 16 bits are identical across three independent samples — `e376c3ae` (2026-10-13 capture, frame 277, dissected in the base finding above), `e376b967` and `e376ba62` (tonight, from the Windows transcript). All three share `e376` in the high half. That value is a byte-for-byte match to the router's own MAC address octets 3–4 (`00:1e:**e3:76**:83:61`), confirmed by direct comparison, not estimation. **HYPOTHESIS:** the bootloader seeds its BOOTREQUEST xid (partly) from its own MAC address rather than a real random/counter source. No security impact demonstrated on its own (BOOTP already has no anti-spoofing to weaken), but it is consistent with — a third independent data point for — the broader pattern already noted in this file: this bootloader's network code reuses predictable, adjacent device state rather than proper randomization or zeroing.

**What was not shown:** no file content was ever served or transferred; no TFTP data-phase behavior, no RBI/image parser exercised, no signature-check behavior observed, no repeat run to confirm reproducibility, no packet capture of the actual reply packet (relying on the script's self-reported log plus the resulting UART behavior, not a byte-level capture of what left the Windows NIC).

**Next (unchanged from before, now actually next instead of first):** run a real TFTP server serving a small, deliberately non-firmware file named `GCNT-X` (not real firmware) to observe how the loader handles a file that exists but is not valid — the first step that actually touches the signature/format-validation code path. Still gated: no real/signed image until that step's outcome is known.

## Addendum (2026-10-27, later same session) — TFTP RRQ confirmed reaching a real server, DATA never ACKed

**Scope:** live, combined BOOTP-reply + minimal single-block TFTP server (`scripts/f1-tftp-serve-test.ps1` / owner-run `C:\bootp_tftp_test.ps1`), same physical setup. Owner-supplied PowerShell transcript (`Start-Transcript`, PID 7872, start `2026-10-27 01:27:35` end `01:30:39`).

**VERIFIED:** `REPLIED to BOOTP! xid=e376bed4 count=1` (single reply this run, vs 2 in the earlier BOOTP-only run). Then, **eleven** times, identically: `RRQ from 192.168.1.2:3984 : file='GCNT-X'` → `sent DATA block=1 bytes=18` → `no ACK received within timeout`. Payload length independently confirmed as exactly 18 bytes for the script's default `"NOT-FIRMWARE-TEST\n"` content. Same source port (3984) on every retry.

**DERIVED:** 11 RRQ retries on the Windows side closely matches the 10× `T` retry count already established from the UART side in the first addendum above — strong corroboration that these are the same phenomenon observed from both ends of the link, not two unrelated issues. The TFTP RRQ **is** reaching a real listener and **is** getting a correctly-shaped DATA response; the failure is specifically that the router never acknowledges it.

**HYPOTHESIS (two non-exclusive candidates, same proposed fix for both):**
1. The bootloader's TFTP client does not implement RFC 1350 TID tracking (the convention that a server replies from a fresh ephemeral port, not the port the request arrived on) and is listening for the DATA reply on port 69 specifically, not wherever the server actually sent from.
2. Windows Firewall is silently dropping inbound traffic to the new ephemeral port the script opened for the reply (never pre-approved), independent of anything the router is doing.

**Not yet distinguished between (1) and (2).** Both predict the same fix: have the server reply from port 69 (the same socket that received the RRQ) instead of a new port. `scripts/f1-tftp-serve-test.ps1` was revised accordingly same day — **untested against the real device as of this addendum.**

**What was not shown:** which of the two hypotheses (or something else) is the actual cause; any loader/parser behavior past the point of a successful transfer, since none has happened yet.
