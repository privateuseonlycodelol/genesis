# BOOT-P on the LAN — Windows pktmon (2026-10-13)

## Result

**VERIFIED:** during a listen-only capture on a Windows PC cabled to the owned F1, the gateway sent classic **BOOTP/DHCP requests** and **nothing answered**.

Ctrl+C on `pktmon` printed “flushing logs”. That writes the log. It did not delete it. The owner transferred `f1-bootp-2026-10-13.txt` and `f1-bootp-2026-10-13.etl`. Private copies: `artifacts/bootp/2026-10-13/` (gitignored). Text is UTF-16, 107,198 bytes. ETL is 419,430,400 bytes. No router HTTP request was made while reading them.

## What was on the wire

pktmon logged **154** port-67/68 events, all **Rx**. Every one is `0.0.0.0:68 → 255.255.255.255:67`. There is **no** Offer, Ack, or packet sourced from port 67.

The bootloader-sized flow (Ethernet **428** bytes, IP length **414**, UDP payload length **386**) is **68** logged copies of **17** unique requests from one client MAC, **00:27:45–00:28:12** local on 2026-10-13. Each request is:

| Field | Value |
| --- | --- |
| Opcode | **1** (BOOTREQUEST) |
| Hardware | Ethernet, length 6; `chaddr` equals the Ethernet source |
| `secs` | 0, then 1, 3, 5 … 27 (about every 2 seconds) |
| Flags | `0x8000` (broadcast reply requested) |
| ciaddr / yiaddr / siaddr / giaddr | all zero |
| `sname` in the logged prefix | empty |

**DERIVED:** 428 bytes is the same length U-Boot logged as `bcmbca_eth_send … len 428` when the port was down ([UART interaction](f1-uart-interaction-2026-10-12.md)). With a link, those frames leave the router. The earlier “BOOTP Reply timeout” is a missing server, not a dead Ethernet port.

pktmon kept **128** bytes of each frame, so the boot filename was missing there.

**VERIFIED (Wireshark full capture, 2026-10-13):** owner file `wan.pcapng-2` (898 KiB, archived `artifacts/bootp/2026-10-13/wan.pcapng`). **17** full **428-byte** BOOTREQUESTs from `00:1e:e3:76:83:61`, `secs` 0–27, broadcast flag. **Boot file name field (ASCII): `GCNT-X`** on every request — board mnemonic for Technicolor signed recovery images, not a `.rbi` path. No BOOTREPLY (`op` 2) to the router in this file. DHCP option area includes vendor-specific **option 43** (Technicolor `ST…` blob; product token `2242AD8AN` visible in hex). Still **no** TFTP transfer and **no** flash in this capture.

Two other source MACs also sent discovers (342-byte and 590-byte frames) in the same window. Those sizes are not the 428-byte bootloader frame. **DERIVED:** other LAN clients asking for a lease while the gateway was rebooting, not a second BOOT-P client. Addresses stay in the private ETL.

Windows also logged shorter “Drop” copies (414, 328, 576 bytes). **DERIVED:** the same three flows after the 14-byte Ethernet header, dropped by the Windows IP stack. They are not extra clients.

## What this does not do

No TFTP read, no firmware offer, no flash, no config key, no root shell. A recovery server was not running. Answering these requests with an image is a separate decision and was not done.

## Addendum (2026-10-27) — byte-exact re-read of `wan.pcapng`, offline only

**Scope:** re-parsed `artifacts/bootp/2026-10-13/wan.pcapng` with `tshark -V`/`-x` plus `scripts/decode_f1_bootp_leak.py` (new, tested: `python3 -m unittest test_decode_f1_bootp_leak` — 8/8 pass). No live router requests. All 17 GCNT-X BOOTREQUESTs in this capture are **byte-identical** to each other in every field below (checked across frames 277, 282, 296, 307, 326, 334, 344, 352, 356, 361, 367, 369, 373, 377, 387, 394, 396) — this is one boot session; a second, independently-booted capture has not been compared.

**VERIFIED — the 128-byte `file` field holds two null-terminated strings, not one:** byte offsets computed from the fixed BOOTP header layout (op/htype/hlen/hops/xid/secs/flags/ciaddr/yiaddr/siaddr/giaddr/chaddr/sname = 236 bytes, `file` field = next 128 bytes) place `file` at absolute offset `0x96`–`0x115` in frame 277. Exact bytes: `47 43 4e 54 2d 58 00 32 33 4b 4e 2f 30 2f 54 4c 00` + zero padding = `"GCNT-X\x00" + "23KN/0/TL\x00"` + padding. Wireshark's own dissector flags this with `[Expert Info (Warning/Undecoded): Trailing stray characters]` on the `Boot file name` field — it only expects one string. `"23KN/0/TL"` is not previously documented anywhere in this repo. **DERIVED (moderate confidence):** this reads as a clean, fully-formed second token (not a fragment), so it is more likely an intentional but undocumented second field — a build/variant/branch tag — riding along in the same buffer as the board mnemonic, than memory corruption. `23` as a leading token is consistent with the `23.1.b` firmware line already associated with this unit elsewhere in the repo, but that is **not** established here; **HYPOTHESIS**, not proof of version.

**VERIFIED — DHCP options 1 (Subnet Mask) and 3 (Router) carry non-address, ASCII-shaped garbage:** option 1 value bytes `55 2d 42 6f` decode as ASCII `"U-Bo"`; option 3 value bytes `2e 61 72 6d` decode as ASCII `".arm"`. Concatenated in on-wire order (option 1 then option 3 then option 6, all 4 bytes each) the 12 bytes read as `"U-Bo.arm\x00\x00\x00\x00"`. Wireshark's own dissector reports these as `Subnet Mask: 85.45.66.111` / `Router: 46.97.114.109` — syntactically valid-looking but semantically nonsensical for a BOOTREQUEST, which has no protocol reason to populate either field with a meaningful value at all (those are reply-side fields). **HYPOTHESIS:** this is an uninitialized or reused stack/heap buffer in the bootloader's BOOTP request builder leaking adjacent memory — possibly a fragment of a path or string like `.../u-boot.arm` — into option slots the code never explicitly sets. Not established: whether this is deterministic per-build (same every boot) or varies run to run; this capture only covers one boot session, so it cannot distinguish "static compiled-in filler" from "genuine stack garbage that happens to be stable within one run."

**VERIFIED (negative) — the option-43 (Vendor-Specific) blob does not walk as clean TLV:** `walk_vendor_specific()` on the real 55-byte blob (skipping the literal `"ST"` 2-byte prefix) stops almost immediately — a claimed length overruns the remaining buffer rather than reaching a sensible `0xFF` End within a consistent option set (regression-tested in `test_decode_f1_bootp_leak.py::test_captured_f1_vendor_blob_does_not_walk_cleanly_as_tlv`). This does not identify what `2242AD8AN` (already noted above) actually is; it only shows the surrounding bytes are not a well-formed generic vendor-option schema either, which is consistent with — but does not prove — the same leaked-buffer explanation as options 1/3.

**What was not shown:** no identification of `2242AD8AN`; no confirmation the file-field second string is a real version/variant code vs. coincidence; no comparison across independent boot cycles to test determinism; no TFTP interaction, no reply sent, no firmware offered.

**Why this matters for the next step:** if the bootloader's own request-encoding path is this casual about buffer initialization, that raises (not proves) the odds that its *reply*-parsing path — the one `f1-bootp-reply.ps1` would actually exercise — has similar weaknesses. This is a reason to prioritize, not substitute for, running the still-unexecuted BOOTP-reply test in [research composite](f1-research-composite-2026-10-13.md) item 1.
