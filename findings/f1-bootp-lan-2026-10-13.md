# BOOT-P on the LAN — Windows pktmon (2026-10-13)

## Result

**VERIFIED:** during a listen-only capture on a Windows PC cabled to the owned F1, the gateway sent classic **BOOTP/DHCP requests** and **nothing answered**.

Ctrl+C on `pktmon` printed “flushing logs”. That writes the log. It did not delete it. The owner transferred `f1-bootp-2026-10-13.txt` and `f1-bootp-2026-10-13.etl`. Private copies: `artifacts/bootp/2026-10-13/` (gitignored). Text is UTF-16, 107,198 bytes. ETL is 419,430,400 bytes. No router HTTP request was made while reading them.

## What was on the wire

pktmon logged **154** port-67/68 events, all **Rx**. Every one is `0.0.0.0:68 → 255.255.255.255:67`. There is **no** Offer, Ack, or packet sourced from port 67.

The bootloader-sized flow (Ethernet **428** bytes, IP length **414**, UDP payload length **386**) is **68** logged copies of **17** unique requests from one client MAC, **00:27:45–00:28:12** local on 2026-10-13. Each request is:

| Field | Value |
| --- | --- |
| Opcode | **1** (BOOTREQUEST) |
| Hardware | Ethernet, length 6; `chaddr` equals the Ethernet source |
| `secs` | 0, then 1, 3, 5 … 27 (about every 2 seconds) |
| Flags | `0x8000` (broadcast reply requested) |
| ciaddr / yiaddr / siaddr / giaddr | all zero |
| `sname` in the logged prefix | empty |

**DERIVED:** 428 bytes is the same length U-Boot logged as `bcmbca_eth_send … len 428` when the port was down ([UART interaction](f1-uart-interaction-2026-10-12.md)). With a link, those frames leave the router. The earlier “BOOTP Reply timeout” is a missing server, not a dead Ethernet port.

pktmon kept **128** bytes of each frame, so the boot filename was missing there.

**VERIFIED (Wireshark full capture, 2026-10-13):** owner file `wan.pcapng-2` (898 KiB, archived `artifacts/bootp/2026-10-13/wan.pcapng`). **17** full **428-byte** BOOTREQUESTs from `00:1e:e3:76:83:61`, `secs` 0–27, broadcast flag. **Boot file name field (ASCII): `GCNT-X`** on every request — board mnemonic for Technicolor signed recovery images, not a `.rbi` path. No BOOTREPLY (`op` 2) to the router in this file. DHCP option area includes vendor-specific **option 43** (Technicolor `ST…` blob; product token `2242AD8AN` visible in hex). Still **no** TFTP transfer and **no** flash in this capture.

Two other source MACs also sent discovers (342-byte and 590-byte frames) in the same window. Those sizes are not the 428-byte bootloader frame. **DERIVED:** other LAN clients asking for a lease while the gateway was rebooting, not a second BOOT-P client. Addresses stay in the private ETL.

Windows also logged shorter “Drop” copies (414, 328, 576 bytes). **DERIVED:** the same three flows after the 14-byte Ethernet header, dropped by the Windows IP stack. They are not extra clients.

## What this does not do

No TFTP read, no firmware offer, no flash, no config key, no root shell. A recovery server was not running. Answering these requests with an image is a separate decision and was not done.

## Next

1. **BOOTP reply test (no RBI yet):** on the cabled Windows PC, run `scripts/f1-bootp-reply.ps1` with `-ClientMac 00-1E-E3-76-83-61` and **`-BootFile GCNT-X`** (default in script). UART should move past `BOOTP Reply timeout` to a **TFTP** error (no file on server). That confirms the reply shape before any firmware is offered.
2. **Only after step 1:** a Technicolor recovery stack must serve a **signed** RBI whose board mnemonic matches **GCNT-X** / this unit — not a random 19.x image. Wrong or unsigned RBI can brick.
