# L598 key as AES-XTS-plain64 against the 19.x reference RBI (2026-10-27)

## Question

Does the 32-byte key printed on UART line 598 (see [f1-rootfs-key-l598-2026-10-27.md](f1-rootfs-key-l598-2026-10-27.md)) decrypt any squashfs in the old 19.x reference image, when used as a dm-crypt `aes-xts-plain64` key?

## Result

**No.** No 512-byte-aligned window of `artifacts/firmware/REFERENCE-GCNT-X-19.x-DO-NOT-FLASH.rbi` decrypts to a squashfs superblock (`hsqs`) under XTS with tweak 0. That is 63,983 windows.

This is a **weak negative**. The test cannot falsify the L598 key with this input. The RBI payload is sealed (`0xB7` AES chunk, [gcnt-x-19x-deep.md](gcnt-x-19x-deep.md)), and the file has no plaintext `hsqs` (`rg -c hsqs` = 0). A plaintext squashfs inside an OSCK-wrapped container would not appear under a raw-file XTS scan at all. So "no hits" says nothing about the L598 key's validity for 23.1.b `rootfs2`. The decisive input is still a raw `rootfs2` volume from the 23.1.b device.

## Method

- Key: read from `artifacts/uart/20261012-193402/raw.log` line 598 by `read_key_from_log()`. The key was never printed or written to a file in this pass. Length is 32 bytes, so AES-128-XTS. This matches a 64-hex-character dm-crypt key.
- Decrypt: `scripts/xts_plain64_squashfs_scan.py`, which uses `cryptography` (50.0.2, scratch venv) with `modes.XTS(tweak=0)`. For each offset P that is a multiple of 512, it decrypts the 512 bytes at P as sector 0 of a dm device starting at P, and reports P if the output starts with `hsqs`.
- Layout assumption: the dm device starts at a 512-aligned offset, so its first sector gets tweak 0. This is the only layout consistent with the device's `crypt aes-xts-plain64 … 0 /dev/dm-0 0` table, which starts at the verity device.

## Controls

- **Unit tests:** `scripts/test_xts_plain64_squashfs_scan.py`, 5 tests, all pass. The key-read tests cover the normal line, the trailing-text case and a rejected short line. The scanner controls are:
  - **Positive:** a real squashfs built with `mksquashfs`, encrypted per sector with plain64 tweaks, embedded at a 4 KiB offset in random data. The scanner finds exactly that offset.
  - **Negative, wrong key:** the same image, with a reversed key, finds nothing.
  - **Negative, no squashfs:** random data finds nothing.
- **Independent XTS:** a pure-Python XTS built on `pyaes` (`/private/tmp/…/scratchpad/xts_independent.py`, scratch only) agrees with `cryptography` on three random 512-byte sectors and on the real RBI sector 0 with the L598 key (`True`). So the scanner's decryption is not a library artifact.
- **OpenSSL CLI:** not usable. `openssl enc` in both the system build and Homebrew OpenSSL 3.5.9 rejects `-aes-128-xts` with "XTS ciphers not supported". This is a tooling limit, not a result.

## What was not shown

- Not shown: that the L598 bytes equal the dm-crypt table key. The table key is masked in every log, and the printed bytes are only linked to it by source reading ([f1-rootfs-key-l598-2026-10-27.md](f1-rootfs-key-l598-2026-10-27.md), check 4).
- Not shown: that the 19.x generation uses the same key family as 23.1.b. The 19.x and 23.1.b devices differ in kernel (4.1.52 vs 4.19.235) and in the boot chain.
- Not shown: any decrypt of the live `rootfs2`. That needs a raw dump.

## Reproduction

```bash
S=<scratchpad>; python3 -m venv $S/xts-venv && $S/xts-venv/bin/pip install cryptography
$S/xts-venv/bin/python -I scripts/test_xts_plain64_squashfs_scan.py
$S/xts-venv/bin/python -I scripts/xts_plain64_squashfs_scan.py \
  artifacts/firmware/REFERENCE-GCNT-X-19.x-DO-NOT-FLASH.rbi \
  --key-log artifacts/uart/20261012-193402/raw.log --key-line 598
```

Expected output: `scanned 63983 aligned windows …` and `squashfs-magic hits: 0`.
