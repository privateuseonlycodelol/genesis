## Source branches

### HTTP access gate and disabled web interface

In `client.c`, ordinary absolute-path requests reach `cupsdIsAuthorized(con, NULL)` before method-specific processing; a non-OK result is returned as an HTTP error and closes the connection ([lines 968–1021](../artifacts/management/cups-source/client.c)). This is the source-level location/access gate relevant to GET, HEAD, and POST. The separate IPP operation handler also applies an operation policy for `CUPS-Get-Printers`, described below.

For GET, once the earlier access gate passes, the disabled-web-interface check applies to paths beginning `/admin` (apart from `/admin/conf/cupsd.conf` and `/admin/log/…`), `/printers`, `/classes`, `/help`, and `/jobs`. If `WebInterface` is false, the branch calls `cupsdSendError(...HTTP_STATUS_CUPS_WEBIF_DISABLED...)` and stops processing ([lines 1177–1196](../artifacts/management/cups-source/client.c)). Thus GET `/admin/` and `/printers/` fall into this source branch. GET `/` does not match that path predicate; it continues through the static-file path after the earlier access gate ([lines 1281–1347](../artifacts/management/cups-source/client.c)).

HEAD has a different branch. After handling specific printer PPD and icon paths, `!WebInterface` clears response fields, sends `HTTP_STATUS_OK` with no content type, logs the request, and stops ([lines 1596–1657](../artifacts/management/cups-source/client.c)). Therefore the generic HEAD disabled-interface branch itself is header-only HTTP 200, not the GET denial. The earlier `cupsdIsAuthorized` gate can still reject a request before this branch.

### POST dispatch and policy boundaries

After request-size checks, POST with the exact content type `application/ipp` allocates an IPP request before the `!WebInterface` check. A POST with another content type is rejected with `HTTP_STATUS_CUPS_WEBIF_DISABLED` when the web interface is off; when enabled, matching web paths are routed to CGI handlers ([lines 1350–1425](../artifacts/management/cups-source/client.c)). The earlier `cupsdIsAuthorized(con, NULL)` check still applies. Once the IPP body is complete, `cupsdReadClient` calls `cupsdProcessIPPRequest(con)` ([lines 1868–2081](../artifacts/management/cups-source/client.c)).

The IPP dispatcher maps `IPP_OP_CUPS_GET_PRINTERS` to `get_printers(con, 0)` ([lines 520–526](../artifacts/management/cups-source/ipp.c)). That handler first calls `cupsdCheckPolicy(DefaultPolicyPtr, con, NULL)` and returns an HTTP error if the policy check fails. Only after the policy passes does it test whether `Printers` is null or empty; in that case it sends IPP status `IPP_NOT_FOUND` with the text `No destinations added.` and returns ([lines 7474–7513](../artifacts/management/cups-source/ipp.c)). For IPP responses, the response writer sends HTTP `200 OK`, content type `application/ipp`, and the encoded IPP response body ([lines 626–678](../artifacts/management/cups-source/ipp.c)). This source path can therefore produce HTTP 200 together with an IPP error status when the policy passes and there are no configured destinations.

In the v2.2.12 template, `WebInterface` is a configure-time placeholder (`@CUPS_WEBIF@`), not a fixed value ([`cupsd.conf.in`, lines 22–23](../artifacts/management/cups-source/cupsd.conf.in)). The template has separate `<Location />` and `<Location /admin>` sections with `Order allow,deny`; `/admin/conf` and `/admin/log` add `AuthType Default` and `Require user @SYSTEM` ([lines 25–47](../artifacts/management/cups-source/cupsd.conf.in)). Its default IPP policy lists specific restricted operation groups and ends with `<Limit All>` containing only `Order deny,allow` ([lines 49–90](../artifacts/management/cups-source/cupsd.conf.in)). `CUPS-Get-Printers` is not named in the template's restrictive operation groups. These are template facts, not evidence that a device uses this generated configuration or that no additional rules apply.

## Relationship to the supplied live observations

The companion live-boundary finding records unauthenticated `CUPS-Get-Printers` responses at `/` and `/admin/` as HTTP 200 with IPP `client-error-not-found` (`0x0406`) and `No destinations added.` It also records GET `/`, `/admin/`, and `/printers/` as HTTP 403 ([management-auth-boundaries-2026-10-12.md](management-auth-boundaries-2026-10-12.md)). Those are supplied live observations; this source review did not repeat them.

The source contains a matching IPP status/message branch and a separate HTTP 200 IPP response writer. That correspondence is consistent with, but does not prove, source/runtime equivalence. The parent reports that the saved 403 body parsed as `Forbidden - CUPS v2.2.10` followed by `Forbidden`; this is a **body-reported version string**, not binary identification. It is a more specific version lead than the `CUPS/2.2` response header, which reports only the family. The installed binary, `WebInterface` value, effective location rules, selected IPP policy, and live destination-array state have not been established from this source retrieval. In particular, neither source version explains the live GET `/` response by the explicit disabled-web-interface GET predicate: `/` is outside it, and location authorization/configuration remains an independent condition.
