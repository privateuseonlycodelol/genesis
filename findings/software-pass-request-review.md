# F1 request-semantics review — offline

**Scope:** local 23.1.b UI artifacts only; no router or ISP requests were made. I inspected the saved HAR, request sidecars, HTML, and recovered JavaScript. The sidecar `*.http` files for the metadata probes contain only status codes, so they do not independently preserve method, URL, or headers.

## Evidence

- **VERIFIED — schedule metadata is a GET.** `artifacts/ui/main-min.js:333-334` calls `$.get("/gateway.lp?action=scheduleReboot")` without a body. In the HAR, the same method and path first returned HTTP 200 `text/html` with login markers; later, after the two `/authenticate` requests and a page reload, it returned HTTP 200 `application/json` with top-level keys `systemTime`, `rebootTime`, `alertMsg`, and `popupHeader`. The first 200 was a login response, not proof that the metadata action ran. No response values are reproduced here.

- **VERIFIED — session-poll source and capture disagree on the path.** `main-min.js:320-321` builds a GET to `/gateway.lp?auto_update=true` and adds `getSessionStatus=true`. The HAR instead records `/login.lp?auto_update=true&getSessionStatus=true` returning JSON with top-level key `current_role`. The separate `gateway-session.json` body also contains that key, but its `.http` sidecar is just `200`. Preserve this discrepancy: the HAR does not verify the source-derived `/gateway.lp` route for that poll.

- **VERIFIED — Smart Wi-Fi status is a GET in the saved page code.** `artifacts/ui/modals-parental-modal.lp.html:76-89` calls `GET /modals/parental-modal.lp?action=smartwifi`; the saved response is JSON with top-level keys `current_state` and `current_phase`, and the sidecar says 200. The code uses these values to show/hide UI and disable Save in one phase. This establishes the client request and saved response shape, not wider authorization or server behavior.

- **VERIFIED — the firmware UI intends two GET metadata calls.** `system-config-min.js:1` sets `target` from the modal form action; the saved form uses relative `modals/system-config-modal.lp` (`modals-system-config-modal.lp.html:19,22`), resolving to `/modals/system-config-modal.lp` in this UI. Lines 14-15 poll `GET target?action=upgradefwstatus` as JSON after an upload; line 17 requests `GET target?action=getbanksize` before upload. Both calls send the action query without a CSRF field. These handlers depend on missing upgrade controls in the saved configuration HTML (`modals-system-config-modal.lp.html:23-38`). The saved GET for `upgradefwstatus` returned the configuration HTML modal (status 200), not the JSON shape the poll expects. No `getbanksize` response was saved in this earlier offline artifact set; a later authenticated live control is documented in [software-pass-config-export.md](software-pass-config-export.md). A query string and HTTP 200 alone do not show that either action was dispatched.

- **VERIFIED — export is a POST download in the frontend.** `system-config-min.js:9-10` binds `.export-config` to `$.fileDownload(target, …)` with `httpMethod: "POST"` and fields `action=export_config` and `CSRFtoken` from the page meta tag. Here `target` is the same `/modals/system-config-modal.lp` form action; `main-min.js:294-298` implements POST download through a submitted form. The saved configuration HTML has no `.export-config` control, and the earlier offline HAR contained no export request. A later authenticated POST succeeded; its response structure is reviewed in [software-pass-config-export.md](software-pass-config-export.md). That later observation demonstrates backend acceptance for that request/session, while the UI markup still does not expose the handler.

- **REPORTED — related public source is not proof about this unit.** The pinned Ansuel source snapshot identified by `artifacts/source-review/manifest.json` commit `ecd493c591afd7de47e624245bd1ac1bd9a526a2` dispatches `export_config` on POST and `upgradefwstatus` / `getbanksize` on GET (`gateway-modal.lp:309-339`). Its export path starts and clears transient RPC export state (`:68-105`). Its `upgradefwstatus` handler calls `os.remove(...)` when state is not `Requested` (`:250-269`), so that GET is not guaranteed side-effect-free in that implementation. This snapshot is not matched to GCNT-X 23.1.b; treat it as a reason to avoid probing status, not as evidence of this router’s behavior. A shared helper in that snapshot checks a submitted CSRF token when a session exists (`web.lua:131-140`), but route applicability and the saved POST’s token/session state are not established, so this does not explain the recorded 403.

## Conclusions to narrow

- **DERIVED:** `findings/f1-bypass-crypto-options.md:19` overgeneralizes from a handful of GETs when it says nginx “allows authenticated GET on many `action=` query strings.” The records show several individual 200s, but `upgradefwstatus` produced ordinary modal HTML; they do not establish general action dispatch.
- **DERIVED:** Its claim that POST to the modal “without going through the in-page form flow is blocked” is broader than the one recorded `POST action=upgradefwstatus` → 403 (`findings/tried.md:28`). The frontend uses GET for that action, so the failed POST is not a valid method comparison and does not establish that the UI flow is what mattered. The saved `.http` file contains only `403`, not the request details.
- **DERIVED:** `findings/f1-api-map.md:66-79` should not read as though all named actions are POSTs or server-supported operations. The JavaScript mixes GET metadata, POST settings/reboot operations, and multipart uploads. Its `rbi`/`fw`/`pkgtb` extension check (`system-config-min.js:16-17`) is client-side only; the UI error string “wrong key” is not evidence that a firmware image was submitted or rejected by this device.
- **UNKNOWN:** The export’s plaintext contents and cryptographic validity, and whether the GCNT-X 23.1.b implementation matches the public source snapshot.

## Tool and next control

Added [`scripts/inspect_ui_har.py`](../scripts/inspect_ui_har.py), which emits only exact allowlisted static paths (unknown paths become `<redacted>`), allowlisted `action` values, method, status, known MIME types, response size, generic login-marker names, and allowlisted JSON key names (unknown keys become `<redacted>`). It omits hosts, other query values, headers, cookies, request bodies, and response values. Running it on the saved HAR produced 22 summaries and showed the HTML-to-JSON `scheduleReboot` contrast. A two-entry synthetic HTML/JSON check with fake host, short unknown path and query strings, header/cookie/password values, unknown short JSON key, and response values passed: no sentinel appeared in serialized output; login markers and allowlisted JSON key names were retained.

**Next ordinary read-only control request (not sent in this offline pass):** in the already-authenticated browser context, issue `GET /gateway.lp` with no query string and no body. Record only status, MIME, response size, login markers, and JSON top-level keys, then compare with the saved same-session `GET /gateway.lp?action=scheduleReboot`. This controls for the base page response while distinguishing the metadata query. Do not use `upgradefwstatus` as a read-only control given the unresolved implementation behavior above.

**Limitations:** the HAR includes sensitive browser material; this note and inspector output contain no cookies, credentials, device serials, or response values. This review did not make live requests; later read-only control results are linked above.
