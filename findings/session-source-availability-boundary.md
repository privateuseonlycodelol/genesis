## Exact 503 and session-capacity path

`sessionmgr.lua` has a session limit predicate: allocation is refused when the manager's total count is at least `maxsessions`, or that remote address's count is at least `maxsessions_per_ip` ([lines 30–44](../artifacts/management/session-source/sessionmgr.lua)). Adding and removing a session increments and decrements those counters ([lines 57–78](../artifacts/management/session-source/sessionmgr.lua)). The manager constructor initializes limits to 50 sessions overall and 10 per remote IP ([lines 820–854](../artifacts/management/session-source/sessionmgr.lua)). The UCI config parser can override both; positive numeric values are used, `-1` means unbounded, and other invalid/nonpositive values fall back to the default ([lines 713–721 and 754–759](../artifacts/management/session-source/sessionmgr.lua)). The live effective UCI values are not present in the fetched source.

A request's cookie is looked up in the manager's session table. A recognized session is rejected by `verifySession` if the stored remote IP differs or the session has expired ([lines 135–181](../artifacts/management/session-source/sessionmgr.lua)). If no valid session is found, `getSessionForRequest` tries `newSession` ([lines 329–336](../artifacts/management/session-source/sessionmgr.lua)). `newSession` returns nil when either capacity limit is reached ([lines 280–297](../artifacts/management/session-source/sessionmgr.lua)). `checkrequest` then calls `redirectIfServiceNotAvailable`; **any nil session at that point** exits with `ngx.HTTP_SERVICE_UNAVAILABLE` and body text `Service not available. Probably too much session open. Wait 20 seconds and retry.` ([lines 306–310 and 361–370](../artifacts/management/session-source/sessionmgr.lua)). The capacity check is therefore a direct source-level route to 503 for requests that need a new session. The 20-second text is emitted to the client; this function does not itself sleep.

`nginx.conf` maps the `default` manager to ports 80 and 443 and uses the `assistance` manager on 8443 ([lines 25–35](../artifacts/management/session-source/nginx.conf)). In the catch-all `location ^~ /`, its access handler obtains the session manager, calls `checkrequest` (with the `auto_update` flag controlling only the `noActivityUpdate` argument), and then calls `handleAuth` ([lines 93–108](../artifacts/management/session-source/nginx.conf)). Thus, for requests handled by this location, the session-availability check occurs before auth-path handling and page content.

One consequence derived from those branches is that a browser with a recognized, unexpired session from the same client IP can continue through `verifySession` without allocating a new session, while a client without a usable session must pass the capacity gate. That makes an existing browser session a plausible explanation for differing browser and cookie-free client outcomes if the limit is reached; it is **not** a finding about the live F1.

## Rate limiting and other 503 hypotheses

No `limit_req`, `limit_conn`, or equivalent request-rate/connection-rate directive appears in the fetched `nginx.conf`, `sessioncontrol.lua`, `sessionmgr.lua`, or `session.lua`. The visible `/api` location applies a 64 KiB body-size limit (`client_body_buffer_size` and `client_max_body_size`) ([nginx.conf, lines 111–122](../artifacts/management/session-source/nginx.conf)); this is a request-size limit, not a request-rate limit. The configuration includes `ui_server.conf`, `main_*.conf`, and `server_*.conf` ([lines 62, 125, and 209](../artifacts/management/session-source/nginx.conf)), but these files are absent from the supplied pinned tree. Therefore this bounded review cannot rule out request/connection limits in omitted includes, another proxy layer, or a different runtime configuration.

The source has a separate brute-force backoff for failed SRP authentication attempts. It is conditional on `mgr.bruteforce == "1"`, tracks failures by username, and returns JSON wait information through the authentication handler ([lines 388–475 and 494–573](../artifacts/management/session-source/sessionmgr.lua)). This path concerns authentication POST processing; the source does not use it to emit the session-availability 503 for an anonymous page request.

## Relationship to the reported runtime behavior

**REPORTED by the parent:** cookie-free anonymous login GETs returned 503 through both urllib and curl, while the browser UI worked. This source review made no router request and did not inspect browser cookies or device logs.

**DERIVED from the pinned source:** exhausted global or per-IP session capacity is a concrete mechanism that can emit 503 when a request needs a new session. It is more directly supported by this source than a generic request-rate-limit explanation. However, the source cannot show whether F1 uses this code, which manager configuration is active, what its counters contain, whether the browser had a reusable session, or whether any proxy/config include supplied another limit. The observed browser/client difference does not by itself distinguish these explanations.

No credentials, cookies, or router interactions were used.
